**Finding 1 — against a small hosted model, self-hosting never pays off
here.** For every assumed configuration, the crossover volume sits
*above* the volume that configuration can physically serve. You would
need to add replicas to reach the volume that justifies the first one,
and each replica moves the crossover up by its own monthly cost. This
script asserts it and exits non-zero if it stops holding.

**Finding 2 — against a mid-tier hosted model, it does.** The same
hardware crosses over at a volume it can serve, because the API side
is roughly 17x more expensive per request while the box costs the same.
The crossover is driven by *which API you are replacing*, not by how
fast the box is.

- 1x A10G-class, 8B model: **224,615 requests/month** (~308/hour sustained)
- 1x A100-class, 70B model: **786,154 requests/month** (~1,077/hour sustained)

## Why throughput is not the lever people expect

| assumed throughput | crossover (req/month) | capacity (req/month) | reachable? |
|---|---|---|---|
| 0.25x baseline | 224,615 | 657,000 | yes |
| 0.5x baseline | 224,615 | 1,314,000 | yes |
| 1x baseline | 224,615 | 2,628,000 | yes |
| 2x baseline | 224,615 | 5,256,000 | yes |
| 4x baseline | 224,615 | 10,512,000 | yes |

**Finding 3 — the crossover volume is invariant to throughput.** Fixed
monthly cost divided by per-request API cost contains no throughput
term. A faster box does not lower the volume at which self-hosting
wins; it only raises the ceiling on whether that volume is reachable.
Asserted above across a 16x throughput range.

This matters because it is the opposite of the usual intuition. If the
crossover is out of reach, buying a faster GPU does not move it closer
— only a cheaper box, a pricier API, or more traffic does. The single
most load-bearing assumption in this file therefore turns out not to
affect the headline number at all, which is a convenient result given
that it is the one thing here nobody measured.
